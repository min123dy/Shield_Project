2. Programs and windows (Windows and Linux)
-------------------------------------------
- shield-gui (Windows: shield-gui.exe, no console): two windows
  · encryption window: Encrypt / Decrypt / Password & keys / Secure delete / Disk cleanup / Algorithms / Settings / Guide
  · file manager (--manager, --open): browse, open .shd, extract some or all, add, delete, check the body
  · arguments used by context menus: --encrypt-multi <items...>, --decrypt <c>, --open <c>, --manager, --settings,
    --wipe [--] <items...> (only opens the Secure delete tab; the checks and the three confirmation steps happen in the
    window, docs/10)
- shield (Windows: shield.exe, console): the command-line program. The MSI adds the install folder to the system PATH;
  the deb installs /usr/bin/shield. Builds with the gui feature also open windows with "shield gui ...".
- Console-only builds (shield-console_v3.1.0_*): one file without any GUI dependency (eframe, rfd ...). The Linux one
  is statically linked with musl.
- Portable: Shield_v3.1.0_x64_portable.exe (a name ending in _portable keeps settings in Shield_data next to the exe),
  Linux AppImage (Shield_v3.1.0_x86_64.AppImage, "cli <command>" runs console commands).
- Explorer starts one process per selected item. Each writes its item into data_dir\spool (secure delete:
  data_dir\spool_wipe); the one holding leader.lck collects until 0.7 s pass quietly (8 s at most) and opens a single
  window, which asks "one container / separately" and lets the user remove or add items. Entries hold only paths,
  NUL-terminated (3.1.0 final: a name containing a newline stays one item); relative paths and file:// URIs are made
  absolute. Unusable items (missing, non-UTF-8 name, too many) are dropped and their count is shown in the window.
  Spool contents are untrusted input and are not used unless the folder is private to the user.

4. Cryptography (same as 2.1.0, nothing weakened)
-------------------------------------------------
- Data, metadata, key slots, temp files: XChaCha20-Poly1305 (256-bit key, 192-bit nonce)
- KDF: Argon2id v1.3, 256 MiB, parallelism 4, iterations 3+PIM (PIM 0-64, default 12)
- Header authentication, encrypted metadata (format version and algorithm IDs only inside), SHA3-512 restore check
- Keys are wiped after each task and never kept; every task asks for the password again (windows and console).
- Passwords: Unicode NFC, at most 256 bytes (longer is refused), constant-time comparison

New uses in 3.0
  settings password   Argon2id (128 MiB, t=3, p=4, 16-byte salt) -> HKDF-SHA3-512("SHIELD-SET-v3") gives a 32-byte
                      verifier and a 32-byte MAC key. Protected values: HMAC-SHA3-512("SHIELD-SET-MAC-v2\n" + text)
                      (the v1 MAC written by 3.0.0 is still read). The MAC key file is sealed with DPAPI + entropy
  random pool         SHA3-512 absorption, output HKDF-SHA3-512(64 OS bytes | pool | counter), remix after output
  updates, integrity  OpenPGP detached signatures (rPGP 0.21; brainpool via RustCrypto bp256/bp384 + ecdsa),
                      SHA-256 from a signed release manifest, HTTPS (ureq 3 + rustls, certificates validated)
  checksum list       SHA-256 (SHA256SUMS.txt, sha256sum -c format)

5. File format v2 (unchanged)
-----------------------------
  [slot 0: 88 B][slot 1: 88 B][nonce prefix 15 B][meta 512 B + tag 16][chunks 64 KiB + tag 16] ...
Header 719 bytes. No magic bytes. Windows and Linux write byte-identical formats; a test opens fixed containers made on
each OS (tests/fixtures/container). 2.x containers open unchanged. Several items bundled into one container are stored
under a folder named after the container and unpack into it.

6. New safety measures in 3.0 (summary; details in 06)
------------------------------------------------------
- Entropy: the OS CSPRNG is always the base and can't be disabled; if it fails, the task stops. Extra sources are only
  mixed in; their state shows only "Normal / Weak" (values are never shown, stored or sent). Console commands never
  collect window state, input timing or mouse data. No /dev/input, no Wayland global coordinates.
- Overwriting: 3 or 7 passes (asked every time, default in the settings), key areas always 7, snapshot warning before
  overwriting, TRIM at the end (failure is shown, the task still succeeds). The old container after rekey, add and
  delete is overwritten too (2.1 did not).
- Updates: off by default, check-only / auto-download, always asked before installing, strict vX.Y.Z tags, same or
  older versions refused, signature failures delete the file and stop, nothing identifying is sent (User-Agent
  "Shield-Updater" only), offline fails silently, secrets wiped before installing, private temp folder. 3.1.0 final:
  installing needs a signed v2 manifest and checks expiry, future issue time, minimum version, revoked keys and rollback
  (the highest release_id seen so far; docs/08 B).
- Console: no-echo secret input, --reveal screen cleared with the scrollback after Enter, argument passwords off by
  default (setting + --allow-arg-secrets + a warning every time), no environment or file input, first Ctrl+C / SIGTERM /
  SIGHUP cancels, the second wipes the entropy pool and exits.
- Secure delete (3.1.0 final): runs only from a ConfirmedWipePlan, which exists only after warning -> limits (checkbox)
  -> 6-character code (3 s wait, 3 wrong answers abort); blocklist (system folders, drive roots, home roots, Shield's
  own files); links and mount points are not followed; file IDs are checked again just before; no weakening option;
  --yes is ignored (docs/10).
- Config folder (3.1.0 final, Linux): only $XDG_CONFIG_HOME/shield or ~/.config/shield (neither set: an error, no /tmp
  fallback). It must be a real folder owned by the user with mode 0700 (looser modes are tightened); settings files others
  can write and a settings.key that is not 0600 are not used. Windows: %LOCALAPPDATA%\Shield (junctions/links refused).
- New-password rules (one place, password::check_new): refused = empty password (no key file), PIM below the default with
  no key file and fewer than 20 characters, confirmation mismatch. Warnings = under 13 characters, one kind of character,
  common passwords, patterns, contains a name, and so on. The GUI allows use after a warning; the console only after a
  direct answer on a terminal or with --allow-weak (not --yes).
- Settings protection: security settings (capture protection, mouse entropy, entropy sources, argument passwords,
  default passes, updates, auto-lock, lock on focus loss ...) change only after entering the settings password. Edits
  from outside break the MAC and reset the protected values to safe defaults. A file without a settings password is
  valid only with the defaults (deleting the auth lines and settings.key leaves the defaults and a warning). Wrong
  passwords wait 1 s, doubling up to 30 s.

7. Known limits
---------------
- Malware running as the same user, administrators/root, the kernel and physical access are not stopped.
- On Linux the settings MAC key file (settings.key) is only a 0600 file, not sealed (Windows uses DPAPI with extra
  entropy: tools that unseal all DPAPI data at once get nothing, a same-user program that knows Shield does). A program
  running as the same user can read it (Linux) or unseal it (Windows DPAPI) and forge the MAC. Settings protection guards
  against other accounts and mistakes.
- Putting back an older settings file (and settings.key) that was valid is not detected (rollback): if the settings
  password has not changed since, its MAC still checks.
- The settings password retry delay is kept in process memory only. A new console run starts at 0. An attacker with
  the same user rights could also reset a counter or delay stored on disk, so none is added. The real protection is
  the Argon2id cost (128 MiB).
- The self check finds changed or damaged programs but not a program whose embedded public key was replaced too.
  Compare the fingerprint shown with the one the developer published separately.
- brainpoolP512r1 signing keys are not supported (256/384, Ed25519, NIST P curves and RSA are, through rPGP).
- A password given as an argument stays in the OS's copy of the command line (Task Manager, /proc/<pid>/cmdline, shell
  history) even though Shield wipes its own copy. That is why it is off by default.
- On the Windows console, TRIM shows a UAC prompt when not elevated; without an answer that stage waits.
- A same-user process can change files between check and use (TOCTOU). Shield re-checks handles, file IDs, sizes and
  times and refuses most cases, but not all.
- On SSDs, flash, COW file systems (btrfs, ZFS), snapshots and cloud folders, overwriting and TRIM don't guarantee
  physical erasure.
- Screen capture protection is not available on Wayland or X11 ("not available, switched off (reason)" in the
  settings).
- Window positions can't be remembered on Wayland (the window manager places windows).
- The AppImage and the GUI use the system GTK3. Without an encrypted swap, memory whose mlock failed can be swapped
  to disk (encrypted swap or none recommended).
- egui copies input events and drawn text internally (same as 2.x).
- Key copies: chacha20poly1305 0.10.1 wipes the key inside the AEAD object on drop (source checked), and since 3.1.0
  the poly1305 zeroize feature is on, so the per-message MAC state is wiped too. That copies left by the compiler in
  registers or on the stack, or pages swapped out, are gone cannot be shown by a test and is not claimed.
- KDF cancel: cancelling after entering the password ends the task at once, but an Argon2id run (256 MiB) that already
  started keeps running in the background until it ends (usually a few seconds). The next derivation starts after it
  (one at a time). Files too short to be a container are refused before the KDF.
- Dependency advisories: rsa 0.9 (RUSTSEC-2023-0071) and crypto-bigint 0.5.5 (RUSTSEC-2026-0387) are only used through
  pgp to verify release signatures with a public key; Shield does no secret-key operation (decrypt, sign) with them.
  There is no fixed rsa release and pgp is tied to crypto-bigint 0.5. webbrowser 0.8 (RUSTSEC-2026-0257) comes with
  egui-winit; Shield drops egui's open-URL requests every frame and uses its own path (Platform::open_url), guarded by
  tests. The reasoning is in .cargo/audit.toml and docs/05; a new advisory fails CI.
- Update install (3.1.0 #1): the verified package is copied into a folder only administrators/root can write, checked
  again and installed. An attacker with administrator/root rights can change that folder too and is outside the threat
  model. Installing in a real UAC / pkexec environment was not tested by hand (docs/06, list of unverified items).
- Update replay: from 3.1.0 final the v2 manifest (issue time, expiry, minimum version, release ID, revoked keys) stops
  it. 3.0.0 and earlier 3.1.0 builds read only v1. The per-user rollback state (update_seen.txt) can be deleted by that
  user, but the elevated installer also checks a separate protected machine-wide state under administrator-only
  ProgramData on Windows or root-only /var/lib/shield/update on Linux. A cross-process lock serializes the privileged
  check, state write and installation. Without a new release within a year the manifest must be signed again (docs/07).
- Bundled release key: keys\release_key.asc must be a valid OpenPGP public key. Direct signing by the primary key, a
  non-expiring key and a personal email user ID are accepted; a signing subkey, project-specific ID and backup key are not
  build or verification prerequisites. Signed tag releases still need a signing-capable secret key matching that public
  key. A dedicated signing subkey and offline backup key are recommended operational hardening (docs/07).
- Secure delete: SSD/NVMe, snapshots, COW, cloud, backups and copies in the recycle bin can keep old data (always shown
  on screen, docs/10 section 5). The confirmation guards against mistakes; it does not stop malware running as the same
  user.
- Update signatures must be binary signatures by a release key that is still unexpired today (review 2 #2). A badly
  wrong system clock can make updates fail (the error mentions the clock).
- Windows: when a normal account creates %ProgramData%\Shield before Shield is installed, the helper does not take that
  folder over and stops the update (review 2 #3); an administrator has to delete the folder. Once installed, the MSI has
  created it administrators-only, so a normal account cannot create it first.
- The MSI has no Authenticode signature, so UAC shows "Unknown publisher". Integrity comes from the OpenPGP signatures
  and the manifest (see the optional task in docs/02).
- No independent (third-party) security audit. The review is static analysis and automated tests, and some items are
  not verified on real systems (docs/09).

8. Verification status
----------------------
See 05_test_and_audit.txt. In short: cargo test --workspace passes on Windows and on Linux (Docker), 0 clippy warnings
on both, cargo audit and cargo deny pass, the Nautilus script test passes. cargo fmt --check does not pass (the code was
never formatted; no effect on behaviour). Not tested by hand: real MSI install/uninstall, an update from a real GitHub
release, the menus on real desktops (GNOME, KDE, Xfce), secure delete results on a real SSD.
