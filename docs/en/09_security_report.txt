0. What this report is (read first)
-----------------------------------
- No independent third-party security audit was done. This is an internal review in which the developer and AI tools
  read the source and wrote tests.
- It is mainly static analysis (reading the source, grep, checking type structure) and automated tests. Some items could
  not be checked on real devices or environments; they are marked "not verified on real systems" (section 7).
- It does not mean "there are no vulnerabilities". What was not found is stated as not found.
- Grades: high (confidentiality/integrity broken remotely or without authentication) / medium (conditions apply, real
  damage possible) / low (limited conditions or impact) / info (not a vulnerability but fixed, or a statement of fact).

1. Scope and method
-------------------
- Input boundaries: container header, metadata and archive (7z/LZMA2/Zstd), settings file and settings.key, spool,
  update manifests (v1/v2) and signatures, command line and environment, drag and drop and file manager arguments.
- Privilege boundaries: Windows UAC update and TRIM helpers, Linux pkexec helper, MSI registrations, context menus.
- New code: secure delete (secure_delete, wipe_view, wipe_cmd, erase.rs), written against the section 4 criteria from
  the start.
- Supply chain: Cargo.lock (cargo audit 0.22.2, cargo deny 0.20.2), build.rs, build.ps1/build.sh, release.yml.
- Tools: cargo test (Windows 10, Docker Linux container), cargo clippy -D warnings (both OSes), clippy.toml
  disallowed-methods, hand-written regression tests. No fuzzing tool (cargo-fuzz) was used; only the random mutation
  tests of fuzz_tests.rs exist.

4. Section 4 results by area (nothing to fix found, or existing measures checked again)
--------------------------------------------------------------------------------------
4-1 Input validation and resources
 - KDF parameters are not read from the header. Argon2id m=256 MiB, p=4, t=3+PIM are code constants (the header has no
   plaintext magic bytes or algorithm IDs); the PIM is user input limited by MAX_PIM=64. No DoS by raising the KDF cost
   through the header.
 - Archives: MAX_FILES entries, depth 64, 1024-character paths, 255-byte components, ratio 10,000, LZMA2 dictionary and
   Zstd window limits. fuzz_tests (randomly mutated containers, broken 7z) are refused without panics. Memory and CPU use
   inside the 7z/Zstd libraries was not verified; the limits above only fence them from outside.
 - Settings, spool, journal, manifests, signatures and key files all apply a size limit to the open handle (A). Spool at
   most 10,000 entries, secure delete plans at most 200,000.
 - Integer conversions: chunk counts and offsets are u64 with checked/saturating arithmetic (earlier review, docs/05); the
   new code (progress, size totals) uses saturating_add/mul.
4-2 Cryptographic implementation
 - Per-chunk nonce = per-container random prefix + kind marker + chunk number (with a last-chunk marker); the AAD binds the
   metadata tag and format marker. Reuse, reordering and truncation are covered by existing tests (container_tests,
   fuzz_tests).
 - Comparisons: key slot DEK, settings MAC and verifier, manifest hashes, secure delete code and token all use
   password::ct_eq (constant time).
 - Decryption failures give one message that does not tell causes apart (err.bad / err.open_bad).
 - Randomness: the OS CSPRNG is always the base; collected entropy is only mixed in (entropy/). Failures are errors, never
   a weaker fallback.
 - zeroize: password input (SecretBuf), Cred, keys and settings keys are Zeroizing. Copies in registers, stack, swap or
   hibernation files cannot be checked (stated in docs/01 section 7).
 - Memory protection: VirtualLock/mlock; Windows error dialogs off, DLL search limited to System32, image load policy;
   Linux RLIMIT_CORE=0, PR_SET_DUMPABLE=0. Failures go through harden::degraded to the user, who must confirm.
4-3 File system and races
 - Secure delete: no-follow opens, handle-based folder listing (fstatat/openat), file IDs compared again, deletion through
   the handle after renaming (docs/10).
 - Temp files: sectemp (private folder, O_EXCL/CREATE_NEW, 0600/owner ACL), journal cleanup after a crash (existing).
 - Spool: not used unless the folder is private; entries older than a minute and malformed entries dropped; the GUI checks
   the content again (untrusted).
 - Reserved device names, 8.3 names, \\?\ paths, ADS, case: archive name checks and dup_key, path_key in secure delete.
4-4 Installation and privilege boundaries
 - Windows: SetDefaultDllDirectories (System32); registry commands quote both the program and %1 (tested); the MSI removes
   earlier versions (pinned UpgradeCode, release_tests). The MSI creates %ProgramData%\Shield with an administrators-only ACL.
 - Linux: pkexec only by absolute path; helper arguments only regular files owned by PKEXEC_UID; polkit auth_admin (not
   remembered).
 - External processes: absolute path candidates only (xdg-open, pkexec, apt-get, dpkg, icacls, msiexec), never a shell.
4-5 Updates and network
 - HTTPS only (redirects included), rustls certificate checks, 5 redirects, 10 s connect / 20 s response timeouts,
   installers at most 512 MiB and small-file limits, fixed allowed file names, the helper verifies its copy again (two
   stages). Manifest v2 (B).
 - A server giving false answers: bad signature -> nothing installed (link only); an old, correctly signed release ->
   refused by expiry and rollback (v2 clients).
4-6 GUI and console
 - Console password arguments are off by default (setting allow_arg_secrets) and warned about when on. Input without echo.
 - Control and spoofing characters and long names in file names: S-09. The GUI shows spoofing characters as <U+XXXX>
   (glyphs::code_only).
 - The limits of clipboard clearing and the environment error display of capture protection stay as in 3.0.0 (docs/01).
4-7 Supply chain and build
 - build.rs: no network; a secret key in the public key file stops the build; the repository URL format is checked.
 - Source zip: stops on a secret key block; secret keys in keys/ and .env excluded (release_tests). Path remapping (S-05).
4-8 Secure delete itself
 - Path resolution errors and relative paths: made absolute and the real path shown
   (relative_items_are_resolved_to_the_real_path).
 - Privilege bypass: nothing above the user's own rights is used (no UAC/pkexec). Read-only flags cleared only after the
   confirmation, through the handle.
 - Getting around the challenge: ConfirmedWipePlan sealed (compile_fail), 3 s / 3 tries / new code, no weakening setting,
   --yes ignored.
 - Reporting failure as success: failed passes, zero-byte writes, failed deletes and failed streams are all "partial /
   failed" (S-06, S-07).
 - Memory: one 1 MiB buffer, plans limited to 200,000 entries.

5. Remaining risks and why they are accepted
--------------------------------------------
 R-1 Malware running as the same user can get around the settings key (on Linux a 0600 file), the per-user update_seen.txt
     and the confirmation. The elevated update rollback floor is stored separately under administrator/root-only access
     and serialized with a lock. Administrators/root, the kernel and attackers with the same elevated rights remain outside
     the threat model (accepted; docs/01 section 7).
 R-2 SSD/NVMe, snapshots, COW, cloud: overwriting and TRIM cannot guarantee physical erasure (accepted; always shown in
     the UI). Remedy: use encrypted volumes or containers from the start.
 R-3 Operational key hardening: the current bundled key has no separate signing subkey, expiry, project-specific user ID
     or backup key. These are recommendations, not cryptographic validity or build prerequisites. A signed release still
     requires a signing-capable secret key matching the embedded public key. A dedicated signing subkey and offline
     backup key are recommended to reduce operational risk (docs/07).
 R-4 The MSI and the programs have no Authenticode signature: SmartScreen warns, and users have to check the GPG .sig
     (docs/04). Not done this time because of certificate cost and handling (accepted).
 R-5 8 advisory exceptions from the old GUI stack (egui 0.27, rfd 0.14) and pgp 0.21: by impact path analysis they are
     features Shield does not use (rsa secret-key operations, webbrowser - links blocked), dependencies not built for
     Windows/Linux (paste: metal for macOS), or advisories whose fixed versions need a GUI stack upgrade (ttf-parser, the
     zbus family). The reason for each is in .cargo/audit.toml. This judgement is the developer's analysis and has not
     been independently verified. Review by 2027-05-10.
 R-6 3.0.0 and earlier-3.1.0 clients read only the v1 manifest and get no replay/rollback protection. It takes effect once
     they are on 3.1.0 final (docs/08 B).
 R-7 rustfmt: cargo fmt --check reports 1,473 differences (the code base was never formatted with rustfmt). No effect on
     behaviour; a mass reformat is hard to review and was not done this time.

6. Recommended follow-up
------------------------
 - Where practical, use an offline certify-only primary, a time-limited signing subkey and an offline backup key
   (docs/07). Publish the fingerprint outside the repository too; these remain recommendations, not build gates.
 - Apply the GitHub settings checklist, then try a tag release (a dry-run tag).
 - An external third-party security audit; long fuzzing of the archive and container parsers with cargo-fuzz.
 - Upgrade egui/eframe, rfd and pgp (removing the advisory exceptions); consider Authenticode signing.
 - The real-system checks in section 7.

8. Follow-up fixes dated 2026-11-11
-----------------------------------
- License: the root LICENSE, Cargo workspace metadata and all four Rust crates now declare Apache-2.0. deny.toml allows Apache-2.0; the workspace's GPL-3.0-or-later declaration was removed.
- Secure-delete guard: Guard::check now compares selected and protected paths in both directions. A selected Shield data-directory descendant (including settings, settings.key and journal files) is refused, as are the directory itself and its ancestors. A regression test covers files, nested folders, the protected root, an ancestor and an unrelated sibling.
- Update rollback: the elevated installer now checks and persists a protected machine-wide state under ProgramData /var/lib. Corrupt, invalid UTF-8 or non-canonical state fails closed. A separate OS lock serializes the check, persistence and installation so concurrent helpers cannot replace a higher rollback floor with an older one.
- Release key policy: the tag/build gate for a particular signing subkey, expiry, project-specific user ID and backup public key, plus the source-pinned fingerprint assertion, were removed. A valid parseable public key remains required; signed releases still require a matching signing-capable secret key.
- Documentation: previous 3.1.0 final change-log references to the release-key gate describe the historical version at that time. Current README, build and key-operation documents clarify that these key-shape attributes are not mandatory.
- Verification limit: cargo/rustc are not installed in the current editing environment, so the new Rust code and tests could not be rebuilt or rerun. No claim is made that the new tests pass. Shell syntax and static source/document checks are performed separately; full Windows/Linux workspace tests and clippy must run in CI with the Rust toolchain. GitHub Actions, UAC/pkexec, and real MSI/deb/AppImage installation were not verified here.

Threat model of the new feature: asking for the settings password before secure delete stops someone else at an
unlocked PC from deleting files with Shield. Programs running as the same user (R-1) can delete files without Shield,
and deleting the settings file (forgotten-password recovery) removes the step from the next start on; neither is
prevented (said in the settings screen and docs/10 2-5).
Structure: execute() needs a sealed WipePermit (compile_fail doc test) that only permit() makes, new for every run.
The console reads it on the terminal only, so scripts cannot skip it.

Looked at again, nothing to fix found: the update helper (argument owner / link / size checks, only the copies are
verified and installed, rollback floor under a lock), archive extraction (private staging folder, entry_ok and dup_key,
create_new, declared size limit), the settings key file (owner and mode checked on the handle), secure delete execution
(checks on the handle, delete after renames). A small race remains: remove_link and remove_dir check the file ID, then
delete by path. Swapping in another object under that name needs write access to that folder (whoever has it can delete
there anyway), so it is accepted.
