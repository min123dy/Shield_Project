=====================================
English: docs\en\05_test_and_audit.txt. 2.x의 기록: docs\history\05_테스트_및_수정_기록_2.x.txt

1. 시험 환경
------------
- Windows 10 Pro 22H2 (x64), Rust 1.99.1 (x86_64-pc-windows-msvc), WiX 5.0.2, Gpg4win
- Linux: Docker, Debian bookworm (rust:1.99-bookworm + GTK3·xkbcommon·wayland·xcb·musl-tools), x86_64
- 직접 확인하지 못한 것: 실제 Linux 데스크톱(GNOME·KDE·Xfce)의 메뉴·창 동작, aarch64 실행, 실제 GitHub 릴리스를
  쓰는 업데이트 전 과정, 사용자의 서명 키로 만든 서명(비밀번호는 사용자만 넣을 수 있음)

새로 더한 테스트의 범위
- 엔트로피: 값 범위, 긴 출력에 반복 블록 없음, 키 생성이 보조 소스를 기다리지 않음, 콘솔에서 창 소스 없음,
  상태는 라벨만(끈 소스는 "꺼짐"), 같은 샘플도 소스가 다르면 다른 풀, health(반복·고정·카운터형 값 거부와 회복)
- 덮어쓰기: 3회·7회 패턴, 바뀐 파일은 거부, 교체 후 새 파일만 남음, 노출 점검과 TRIM 실패가 작업을 실패시키지
  않음, 읽기 전용 파일 처리. Windows: 권한이 없으면 섀도 복사본이 "없다"고 단정하지 않음, ReTrim 도우미 인수 검사.
  Linux: 권한 없는 TRIM은 안내나 명확한 답
- 업데이트: 태그 해석(vX.Y.Z만. 3.0.1, v3.0, v3.0.1-rc1, v03.0.1, V3.0.1, 전각 숫자 등 거부), 같은·낮은 버전과
  초안·사전 릴리스 무시, 다른 곳을 가리키는 파일 무시, 매니페스트 형식 엄격, 서명·해시·버전 중 무엇을 바꿔도 실패,
  패키지 이름 규칙
- OpenPGP: 고정된 실제 서명(Ed25519, brainpoolP384r1)으로 정상, 부키 서명, 데이터 변조·다른 키 거부,
  폐기된 키 거부, 잘못된 입력은 패닉 없이 오류, 파일 크기 제한
- 설정 비밀번호: 생성·해제·변경·삭제, 틀린 비밀번호, 파일 변조 감지 후 보호 항목 초기화, 지연 증가
- 여러 항목: 스풀 모으기(리더 하나), 중복 제거, 묶음 이름 규칙, 묶음 컨테이너의 복호화 폴더
- 형식: Windows와 Linux에서 만든 고정 컨테이너를 서로 열기 (cross_os_tests)
- CLI: 해석기(옵션·값·--·알 수 없는 명령), 비밀 입력 키 처리(Enter, Esc, Ctrl+C/D/U, Backspace), 인자 비밀번호
  거부(설정 꺼짐 / 플래그 없음), 종료 코드(틀린 비밀번호 3, 서명 불일치 4), encrypt-list-add-remove-decrypt 전
  과정, 묶기·따로, keyfile, verify, entropy 스위치(os는 끌 수 없음, 설정 비밀번호 필요)
- GUI: 모든 탭과 설정 분류를 화면 없이 그려 패닉이 없는지, 다중 선택 처리, 덮어쓰기 확인 창 문구
- 문자열: 한국어·영어 키 일치, {} 개수 일치, 오류 코드 형식, 모든 화면 문자가 글꼴에 있는 문자인지

3. 발견해서 고친 문제 (2.1.0에 있던 것)
---------------------------------------
B1  Linux에서 남은 임시 폴더 판단: 2.1은 자기 pid만 알아 다른 Shield 프로세스가 쓰는 스테이징 폴더를 남은
    폴더로 알렸고, [지금 삭제]를 누르면 다른 작업의 임시 파일을 지울 수 있었습니다. -> /proc/<pid>/stat의 시작
    시각으로 살아 있는 소유자를 확인합니다.
B2  Linux에서 결과 이름 정하기 경쟁: "이름이 없으면 rename" 사이에 다른 프로세스가 같은 이름을 만들면 덮어썼습니다.
    -> renameat2(RENAME_NOREPLACE). 지원하지 않는 파일 시스템에서 파일은 link+unlink,
    폴더는 확인 후 rename(작은 경쟁이 남음)으로 대체합니다.
B3  Linux에서 rename 뒤 폴더 fsync가 없어 정전 시 새 이름이 사라질 수 있었습니다. -> 폴더 fsync.
B4  Linux 데이터 폴더가 $HOME/Shield였습니다. -> XDG($XDG_CONFIG_HOME/shield, 0700).
B5  전체 키 교체·파일 추가·항목 삭제가 이전 컨테이너를 그냥 지워(unlink) 이전 키 슬롯과 암호문이 디스크에
    남았습니다. 이전 비밀번호를 아는 사람은 디스크 복구로 열 수 있었습니다. -> 교체 후 이전 파일을 고른 횟수로
    덮어쓰고 키 영역은 7회.
B6  Linux에서 지우면 안 되는 상위 폴더 검사가 경로 길이(3자 이하)만 봐서 /usr, /etc 같은 폴더를 막지
    못했습니다(이름 검사 덕분에 실제 삭제까지 가지는 않음). -> 시스템 폴더 목록과 /proc·/sys·/dev 거부.
B7  Linux 사용 가능 메모리를 _SC_AVPHYS_PAGES(캐시 제외)로 읽어 너무 작게 보고, 큰 파일에서 압축 사전을 불필요하게
    줄이거나 복호화를 거부할 수 있었습니다. -> /proc/meminfo MemAvailable.
B8  Linux 한글 글꼴 경로가 Debian·Ubuntu에 없는 경로였습니다(글자가 네모로 보임). -> 배포판별 후보 목록.

4. 3.0 작업 중 발견해서 고친 문제
---------------------------------
N1  콘솔 shield.exe가 TRIM 관리자 도우미 인수를 받으면 알 수 없는 명령으로 끝났습니다(UAC 승인 후 TRIM이 실행되지
    않음). -> 콘솔에도 도우미 처리를 맨 앞에 넣었습니다.
N2  포터블 exe에서 업데이트가 MSI 설치를 제안했습니다(설치되지 않은 포터블을 MSI로 덮게 됨). -> 포터블은 릴리스
    페이지만 알립니다.
N3  MIME 정의에 존재하지 않는 매직 바이트를 넣었습니다. 형식 v2에는 매직이 없습니다(의도된 설계: 파일만 보고 Shield
    파일임을 알 수 없게). -> 확장자(*.shd)만.
N4  GitHub Actions에서 한 단계의 if가 그 단계의 env를 볼 수 없어 서명 단계가 항상 건너뛰어졌습니다. -> 작업 단위 env.
N5  탐색기에서 .shd 하나를 넘기면 파일이 실제로 있어야만 복호화로 갔습니다. -> 확장자로 판단하고, 없으면 오류.
N6  CLI 테스트가 TRIM 단계에서 UAC 창을 기다리며 멈췄습니다. -> 테스트에서는 TRIM을 끕니다(제품 동작은 그대로).
N7  서명 빌드(-Sign)에서만 MSI가 실패했습니다(WIX0367: 버전 없는 .sig 두 개가 한 구성 요소에 있어 자동 GUID 불가).
    서명 없는 시험 빌드에서는 그 구성 요소가 빠져 드러나지 않았습니다. -> .sig마다 구성 요소를 나누고, 가짜 .sig로
    Signed=yes 빌드를 ko-KR·en-US 모두 확인했습니다.
N8  MSI 설치 주의사항(RTF)의 한글이 깨졌습니다(예: "¡á Shield 3.0.0 ¼³Ä¡ ¾È³»"). 949 코드 페이지 바이트(\'xx)를
    글꼴 문자 집합 없이 넣어, 비유니코드 프로그램용 언어가 한국어가 아닌 PC에서 다른 코드 페이지로 읽혔습니다.
    -> ASCII가 아닌 글자는 모두 RTF 유니코드 이스케이프(\uN)로, 글꼴에 \fcharset129. RichEdit에 넣어 원문과
    같음을 ko-KR·en-US 모두 확인, ANSI 글꼴로 바꿔도 한글이 그대로 보임을 확인했습니다.

5. 보안 재점검 (§9 항목별)
--------------------------
경쟁 조건
  - 결과 파일: 새 이름 만들기는 create_new / RENAME_NOREPLACE / MoveFileEx(덮어쓰기 없음)만 씁니다.
  - 컨테이너 수정: 프로세스 간 잠금(쓰기 단독, 읽기 공유). 열어 둔 사이에 바뀐 컨테이너는 교체하지 않습니다(크기·
    시각·파일 ID 비교).
  - 여러 항목 모으기: leader.lck을 잡은 프로세스만 창을 열고, 목록 파일은 create_new로 만듭니다.
  - 남은 위험: 같은 사용자 권한의 프로세스가 검사 직후 파일을 바꾸는 것(TOCTOU)은 핸들 고정과 재확인으로 줄였지만
    완전히 막을 수는 없습니다.
임시 파일
  - 평문 스테이징 0700 폴더 + 기록 파일, 암호화된 SecTemp(무작위 키, 블록 인증), 업데이트 다운로드는 사용자 전용
    폴더에서 실패 시 삭제. 스풀 목록은 경로만 담고 사용자 전용 데이터 폴더(0700) 안에 있으며 읽은 뒤 삭제.
경로 조작
  - 압축 해제: ..·절대 경로·드라이브 문자·예약 이름·NUL·링크 항목 거부, 실제 경로가 대상 폴더 안인지 다시 확인.
  - 업데이트 파일 이름: 매니페스트에서는 버전과 OS로 정해지는 이름(Shield_v<V>_x64.msi 등)만 찾으므로, 매니페스트나
    릴리스가 주는 이름이 사용자 전용 다운로드 폴더 밖을 가리킬 수 없습니다.
메모리 잔존
  - 비밀번호·키·키 파일 지문·엔트로피 풀·설정 비밀번호 유도값은 Zeroizing/SecretBuf, 끝나면 지움. CLI는 argv
    사본을 지우고, 입력 버퍼를 zeroize합니다. Ctrl+C·SIGTERM·SIGHUP 처리기가 취소 후 풀을 지웁니다.
  - 남은 위험: OS가 가진 명령줄 사본, egui 내부 복사, 스왑(mlock 실패 시).
인자 노출
  - --password 계열은 기본 거부(설정 + --allow-arg-secrets 두 조건). 매번 경고. --json·--quiet 출력에는 이름·크기·
    개수만 있습니다. 비밀 정보를 환경 변수·파일·표준 입력 파이프로 받지 않습니다(터미널이 아니면 거부).
업데이트 변조
  - HTTPS + rustls 인증서 검증, https 아닌 리다이렉트 거부, 응답 크기 제한, 태그 엄격 해석, 서명된 매니페스트의
    버전이 태그와 같고 현재보다 높아야 함, 해시 일치, 설치 파일 자체 서명. 하나라도 실패하면 삭제·중단.
  - 서명된 이전 버전 설치 파일을 새 태그로 다시 올리는 공격: 매니페스트 버전 확인으로 막습니다.
  - 남은 위험: 내장된 키의 비밀키(서명 부키)가 유출되면 막을 수 없습니다(부키 만료·폐기 권장).
서명 우회
  - rPGP가 발급자·해시 접두사·바인딩 서명·부키 서명 기능·역서명을 확인. Shield는 문서/텍스트 서명만 허용하고
    MD5·SHA-1·RIPEMD-160 거부, 폐기된 부키 거부. brainpool은 RustCrypto의 검증 함수로 마지막 단계만 수행(직접 만든
    암호 코드 없음). 테스트에 변조·다른 키·폐기된 키 경우가 있습니다(약한 해시 거부는 코드 검토로만 확인).
TOCTOU (그 밖)
  - 원본 파쇄: 목록 확정 때의 파일 ID·크기·시각과 다르면 건드리지 않음. 덮어쓰기는 같은 핸들로 수행.
  - 업데이트: 검증한 파일을 같은 사용자 전용 폴더에서 바로 설치 프로그램에 넘깁니다. 같은 사용자 권한의 프로세스가
    그 사이에 바꿀 수 있다는 위험은 남습니다(같은 사용자 권한의 악성 코드는 위협 모델 밖).
엔트로피
  - OS 난수가 항상 기본이고 실패하면 중단. 보조 소스는 키를 혼자 만들지 않으며 값은 내보내지 않음. /dev/input·전역
    좌표 미사용. 콘솔은 창 소스 끔.
빌드·배포
  - 저장소 URL과 공개키는 build.rs가 검사, 비밀키가 섞인 .asc는 빌드 중단. 소스 zip에서 비밀키 블록을 찾으면 중단.
    서명 비밀번호는 스크립트를 거치지 않음. CI 시크릿은 임시 GNUPGHOME에서만 쓰고 지움.

6. 보안이 더 강한 쪽을 택한 결정
--------------------------------
- 키 교체·추가·삭제 뒤 이전 컨테이너 덮어쓰기(2.1은 하지 않음): 시간이 더 걸리지만 이전 비밀번호로 디스크에서
  복구되는 것을 줄입니다.
- 설정 비밀번호가 없으면 보안 설정은 바꿀 수 없습니다(3.0 첫 실행 때 기본값 유지). 바꾸려면 먼저 만듭니다.
- 설정 파일 MAC이 맞지 않으면 보호 항목을 사용자가 바꾼 값이 아닌 안전한 기본값으로 되돌립니다.
- SSD에서도 기본 덮어쓰기는 7회입니다(2.1의 SSD 1회 기본 대신, 3회는 사용자가 고를 때만).
- 콘솔은 표준 입력 파이프로 비밀번호를 받지 않습니다(스크립트 편의보다 노출 방지).
- 업데이트는 서명이 없는 릴리스를 설치하지 않습니다. 공개키 없이 만든 빌드는 업데이트를 설치할 수
  없다고 알립니다.
