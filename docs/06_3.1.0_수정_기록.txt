SHIELD 3.1.0 - 수정 기록 (3.0.0 -> 3.1.0)
=======================================
English: docs\en\06_changes_3.1.0.txt. 3.0 설계와 변경: 06_3.0.0_수정_기록.txt. 키 교체: 07_서명키_교체.txt
이 문서는 "이전 3.1.0 빌드"까지의 기록입니다. 3.1.0 최종(수정 후)에서 더한 변경은 08_3.1.0_최종_변경_내역.txt,
보안 분석은 09_보안_분석_보고서.txt에 있습니다. 아래 0절의 "비밀번호 정책 그대로"와 "매니페스트 형식 그대로"는
이전 3.1.0 빌드 기준이며, 최종에서는 CLI --allow-weak와 v2 매니페스트(v1은 그대로 함께 게시)가 더해졌습니다.

두 번의 정적 점검에서 나온 항목 1~5, 7~13과 새 기능 14("SHIELD에서 열기")를 반영한 릴리스입니다. 항목 6(비밀번호
정책)은 범위 밖이라 바꾸지 않았습니다. 작업 순서는 10 -> 1 -> 3 -> 4 -> 5 -> 11 -> 12 -> 13 -> 14 -> 2 -> 8 -> 9 -> 7 -> 15.

0. 지킨 불변 조건
-----------------
- 비밀번호 정책(engine.rs min_password_len, password.rs check_new/weak_reasons, 번역·테스트)은 그대로입니다.
- 3.0.0 -> 3.1.0 자동 업데이트: 매니페스트 형식("Shield release manifest 1" / "version X.Y.Z" / "sha256 <hex> <이름>"),
  배포 파일 이름과 .sig 쌍, 주 키 서명이 그대로입니다. compat_tests가 3.0.0의 parse_manifest 원문(테스트 자료로
  보관)이 지금 코드에 그대로 있는지, 3.1.0 매니페스트를 읽는지 확인합니다.
- FORMAT_VERSION 2, 설정 SCHEMA 2, Settings::protected_text(compat_tests가 3.0.0 원문과 비교), MSI UpgradeCode는
  그대로입니다. 기존 구성 요소 GUID는 바꾸지 않았고, .shd 전용 "열기" 구성 요소 하나만 새 구성 요소로 대체했습니다(14번).
- XChaCha20-Poly1305 사용, nonce 방식, 파일별 DEK, Argon2id(256 MiB, p=4, t=3+PIM), 메타데이터 인증, 추출 전 전체
  인증, 복원 검증, 아카이브 경로·크기 검사는 바뀌지 않았습니다.
- 테스트는 지우거나 약하게 바꾸지 않았습니다. 3.0.0의 테스트 230개는 모두 남아 있고(이름 비교), 47개를 더했습니다.
  내용이 바뀐 기존 테스트 5개는 12절에 이유를 적었습니다.

1. 업데이트: 검증과 설치 사이의 바꿔치기 [중간] (3.1.0 #1)
----------------------------------------------------------
문제: 3.0.0은 사용자 폴더(%TEMP%, 런타임 폴더)에서 검증한 패키지를 msiexec / pkexec apt-get에 그대로 넘겼습니다.
UAC·암호 창이 떠 있는 동안 같은 사용자 권한의 프로그램이 파일을 바꾸면 바뀐 패키지가 관리자 권한으로 설치될 수
있었습니다.
수정:
- 공통(shield-core update.rs): 권한 있는 도우미 update::helper_main. 받은 네 파일(패키지, .sig, 매니페스트, .sig)을
  믿지 않고 링크를 따르지 않고 읽어, 관리자/root만 쓸 수 있는 새 폴더로 복사한 뒤 "복사본"을 내장 키·현재 버전으로
  다시 검증하고 복사본으로만 설치합니다(verify_and_install_privileged, verify_copies). 실패하면 폴더를 지웁니다.
- Windows(shield-platform windows/install.rs, sys.rs): 설치된 shield-gui.exe(Program Files 아래)만 UAC로
  --install-update <4 파일>을 실행합니다. 포터블·개발 빌드는 승격하지 않습니다. 복사 폴더는
  %ProgramData%\Shield\update\<난수>, 보호된 DACL(SYSTEM·Administrators만, 상속 없음). msiexec가 실행 중인 Shield
  파일과 부딪히지 않도록 도우미가 자신을 그 폴더로 복사해 2단계(--install-update-run <폴더>)를 실행하고, 2단계가
  System32의 msiexec로 복사한 MSI를 설치한 뒤 파일을 지웁니다(실행 중인 exe와 폴더는 다음 재부팅 때).
- Linux deb(linux/install.rs, sys.rs, shield-cli): pkexec는 root 소유 /usr/bin/shield update-install <4 파일>만
  실행합니다(polkit 정책 installer/linux/com.shield.update.policy, auth_admin). 복사 폴더는
  /var/lib/shield/update/<난수>(root 소유; 2차 검토 19-1에서 폴더 0711, 사본 0600, 검증 뒤 package.deb만 0644로 바뀜). 도우미는 pkexec로
  root로 실행된 경우에만 동작합니다. postrm purge에서 /var/lib/shield를 지웁니다.
- AppImage: 새 AppImage를 기존 파일 옆에 쓰고(0755, fsync), 이름을 바꾸기 직전에 그 파일의 SHA-256을 서명된
  매니페스트와 한 번 더 비교합니다.
테스트: update_tests(helper_arguments_are_checked, copies_are_verified_and_later_changes_to_the_originals_do_not_matter,
helper_refuses_to_run_unprivileged_and_reports_outcomes), windows/tests(update_private_folder_has_admin_only_protected_dacl,
helper_command_line_quoting_refuses_what_it_cannot_quote, only_programs_below_program_files_are_elevated_for_updates,
second_stage_arguments_are_checked), linux/tests(update_helper_runs_only_as_root_from_pkexec,
update_folders_must_be_root_owned_and_closed, update_files_are_new_and_world_readable).
남은 한계: 관리자/root 권한의 공격자는 위협 모델 밖입니다. 실제 UAC·MSI와 실제 pkexec·polkit으로 하는 설치는 직접
실행하지 못했습니다(14절 미확인).

2. 릴리스 서명 키 분리와 CI 강화 [중간] (3.1.0 #2)
-------------------------------------------------
- build.ps1 -Stage all|build|package|manifest(-BinDir), build.sh --stage ...(--bin-dir). 기본 all은 예전과 같습니다.
  package 단계는 서명하지 않고 프로그램 .sig는 둘 다 있거나 둘 다 없어야 합니다. 모든 cargo 호출에 --locked.
- .github/workflows/release.yml을 audit -> build-windows / build-linux -> sign-binaries -> package-windows /
  package-linux -> sign-release -> publish로 다시 썼습니다. 서명 작업만 environment release-signing을 쓰고 v* 태그
  push에서만 실행됩니다. 빌드·패키지 작업에는 비밀 정보가 없고, 서명 작업에는 cargo·패키지 설치·서드파티 액션이
  없습니다. 비밀번호는 --passphrase-fd 0으로만 전달(파일 없음). 모든 uses:는 커밋 SHA로 고정했습니다(git ls-remote로
  조회: actions/checkout v4.3.1 34e1148..., upload-artifact v4.6.2 ea165f8..., download-artifact v4.3.0 d3f86a1...;
  TODO-PIN 없음). workflow_dispatch는 서명·게시를 건너뜁니다.
- .github/dependabot.yml(cargo, github-actions 매주), deny.toml(cargo-deny 0.20.2: advisories·bans·sources·licenses),
  CI에서 cargo audit --deny warnings. 이를 위해 .cargo/audit.toml에 "유지보수 중단" 알림 5건(paste, ttf-parser,
  zbus_names, zvariant, zvariant_derive)을 출처와 함께 추가했습니다. 내부 크레이트에 publish = false(cargo deny가
  path 의존성을 와일드카드로 보지 않도록).
- 검사 테스트(release_tests): release_workflow_keeps_secrets_out_of_builds, every_cargo_build_is_locked,
  release_manifest_and_asset_names_are_unchanged.
- 확인: Windows에서 build.ps1 세 단계를 저장소 복사본으로 실행해 MSI·포터블·콘솔·소스 zip과 3.0.0과 같은 형식의
  매니페스트를 만들었습니다. Linux 단계 결과는 13절. 워크플로 자체는 GitHub에서 실행하지 못했습니다(미확인).
- docs/02 7절에 구조, environment 설정 절차, SHA 고정·dependabot 운영을 적었습니다.

3. 릴리스 서명 검증: 시각·만료 확인과 백업 키 [낮음~중간] (3.1.0 #3)
-------------------------------------------------------------------
- rPGP(pgp 0.21) 소스 확인 결과: verify는 발급자, 해시 강도·접두사, 서명값만 보고 시각·만료는 보지 않습니다.
  그래서 sigverify.rs check_times가 직접 확인합니다: 생성 시각 있음, 서명 키 생성 이후, 현재보다 하루 넘게 미래가
  아님, 서명 만료 전, 서명 당시 서명 키(와 주 키)가 만료 전. 주 키로 직접 서명한 경우 sign 플래그 필요(부키는
  바인딩에서 확인). 시각 오류는 E_SIGTIME 코드와 "시스템 시계 확인" 안내(sig.before_key/future/expired/key_expired).
- 백업 공개키: keys/release_key_backup.asc 또는 SHIELD_PUBKEY_BACKUP_PATH. build.rs가 공개키만 받아 내장(비밀키면
  중단), buildinfo::release_keys()가 주 키, 백업 키 순서로 돌려줍니다. 둘 중 하나로 검증되면 통과하고 Verified에
  어느 키인지 담깁니다. 정보 화면과 shield version이 두 지문을 보여 줍니다(JSON: backup_fingerprint).
- 저장소에는 아직 백업 키가 없습니다. 만들고 넣는 절차와 유출 대응은 docs/07. 3.0.0은 백업 키를 모르므로 3.1.0이
  먼저 퍼져야 효력이 있습니다.
테스트: sigverify_tests(plain_and_far_expiring_signatures_still_verify, expired_future_and_early_signatures_are_refused_
with_a_clock_hint, time_rules_table, revoked_signing_subkey_is_refused, primary_without_sign_flag_is_refused,
backup_key_signature_is_accepted_and_named). 테스트 키는 테스트 안에서 만들거나 기존 자료를 썼고 개인키를 저장소에
넣지 않았습니다.

4. 파일 이름 위장 문자 [낮음~중간] (3.1.0 #4)
--------------------------------------------
- archive.rs: 방향 제어 문자(U+202A~202E, 2066~2069, 200E, 200F, 061C)와 U+FEFF를 위장 문자로 봅니다(ZWJ/ZWNJ는
  한글·이모지 등에 쓰이므로 제외). 목록·위치 표시줄·정보 창은 "<U+202E>"처럼 보이게 표시하고(display_name), 추출할
  때는 '_'로 바꿉니다(sanitize_component, 모든 경로 조각). 바꾼 뒤 이름이 겹치면 추출을 멈춥니다(arc.spoof_clash).
  바꾼 파일과 desktop.ini, .library-ms, .searchconnector-ms, .scf, .url 같은 위험한 Windows 형식은 결과에 알립니다.
- 단일 파일 복호화(engine.rs)의 이름도 같은 규칙. GUI 관리자 창과 CLI list는 표시용 이름을 쓰고, JSON은 실제 이름.
테스트: container_tests(spoof_characters_are_listed_but_replaced_on_extraction, names_that_collide_after_replacement_
stop_the_extraction, spoof_set_and_display_escaping, decrypted_single_file_name_is_cleaned_too).

9. 기타 확인·보강 (3.1.0 #9)
---------------------------
9-A 키 복사본: chacha20poly1305 0.10.1 소스(레지스트리) 확인 - ChaChaPoly1305에 Drop(key.zeroize)과 ZeroizeOnDrop이
    있고 chacha20의 zeroize 기능을 켭니다. poly1305의 zeroize 기능은 켜지 않아 메시지별 MAC 상태(r, h, pad)는
    지워지지 않았습니다. shield-core가 poly1305 = { features = ["zeroize"] }를 직접 지정해 켰습니다(Cargo.lock은
    의존 관계 두 줄만 바뀜, 새 크레이트 없음). 테스트 aead_key_and_mac_state_are_wiped_on_drop(ZeroizeOnDrop 트레이트
    확인, 설정 유지). 메모리 내용 자체는 테스트로 증명할 수 없으며 그렇게 주장하지 않습니다(docs/01 7절).
9-B Nemo: Nemo 소스(linuxmint/nemo master, nemo-action.c, eel-string.c)를 확인했습니다. Quote=double이면 %F의 각
    경로를 큰따옴표로 감싸고 안의 " 와 \ 만 이스케이프하며, Exec 줄은 셸 없이 g_spawn_command_line_async
    (g_shell_parse_argv)로 나눕니다. 같은 방식으로 Exec 줄을 만들어 실제 GLib(2.84.4, Debian trixie)로 나눠 보는
    검사(installer/linux/tests/nemo_quote_check.c)에서 공백, 따옴표, $(...), 백틱, \, 줄바꿈, ;|&>, 끝의 \,
    $HOME, "--open" 이름 12개가 모두 원래 이름 그대로 인자 하나가 되었고 아무것도 실행되지 않았습니다. 그래서
    Quote=double을 유지했고, 세 Nemo 액션(암호화·복호화·열기)과 사용자별 액션 모두 Quote=double입니다. 실제 Nemo
    화면에서의 동작은 확인하지 못했습니다(배포판의 Nemo 버전이 master와 다를 수 있음, 미확인).
9-C build.ps1은 빌드 단계에서 rustc 호스트가 x86_64-pc-windows-msvc가 아니거나 CARGO_BUILD_TARGET이 MSVC가 아니면
    중단합니다(/DEPENDENTLOADFLAG는 MSVC 전용). release_tests가 검사 문장이 있는지 확인합니다.
9-D MSI Authenticode: 구현하지 않고 docs/02 7절에 선택 과제(순서: MSI -> Authenticode -> 매니페스트 해시 ->
    OpenPGP, 인증서 키는 서명 environment 안에서만)로 적었습니다.
9-E 의존성 권고: (1) RUSTSEC-2023-0071 rsa 0.9 - 고쳐진 버전 없음. (2) RUSTSEC-2026-0387 crypto-bigint - 권고의
    patched 범위는 >= 0.7.6. Cargo.lock에는 0.7.10(bp256/bp384 -> elliptic-curve 0.14, 해당 없음)과 0.5.5(pgp 0.21

10. Linux 디렉터리 순회의 fail-open [중간, 가장 먼저] (3.1.0 #10)
-----------------------------------------------------------------
문제: manifest.rs는 열린 항목의 실제 경로를 읽지 못하면(/proc이 없는 Linux 등) "안에 있음"으로 보았습니다.
수정: 항목을 잡고 있는 폴더 핸들 기준으로 찾고 엽니다(Linux fdopendir/fstatat/openat + O_NOFOLLOW, Windows는 잡은
폴더의 이름을 바꿀 수 없음). 열린 폴더·파일마다 실제 경로를 부모와 비교하고, 읽지 못하면 전체 검사를 멈춥니다
(directly_in에서 "알 수 없음 = 안"이 사라짐). 파쇄 직전에 모든 원본이 선택한 항목 안에 그대로 있는지 핸들로 다시
확인하고(recheck_roots), 확인할 수 없으면 아무것도 덮어쓰지 않습니다(암호화 결과는 남음, ShredReport.refused).
목록 안의 링크와 FIFO는 따라가지 않고 건너뜁니다.
테스트: manifest(directly_in_is_fail_closed, unknown_real_path_stops_the_scan, entry_of_a_folder_without_known_real_path_
is_refused, shred_is_refused_when_originals_cannot_be_rechecked, encrypt_with_shred_does_nothing_without_real_paths,
links_and_fifos_inside_are_skipped_not_followed).

11. Linux 폴더 이동 폴백의 덮어쓰기 경쟁 [낮음] (3.1.0 #11)
---------------------------------------------------------
renameat2(RENAME_NOREPLACE)를 못 쓰는 파일 시스템의 폴백: 파일은 hard_link(이미 있으면 실패) 후 원래 이름을
지우고, 지우지 못하면 링크를 되돌립니다. 폴더는 대상의 부모가 현재 사용자 소유이고 그룹·다른 사용자가 쓸 수 없을
때만(dir_fallback_ok) 옮기고, 아니면 번역된 메시지(eng.noreplace_dir)로 거부합니다.
테스트: linux/tests(folder_fallback_rule_table, fallback_moves_files_by_link_and_folders_only_into_closed_folders),
engine_tests(refused_folder_move_reads_as_a_translated_message).

12. 임시 파일 정리 시 재확인 [낮음] (3.1.0 #12)
----------------------------------------------
SecTemp와 PartGuard는 만들 때의 파일 ID(볼륨·인덱스)를 기억하고, 지우기 전에 링크를 따르지 않고 열어 같은 파일인지
확인합니다(sysinfo::remove_if_same). 다른 파일이 그 이름을 차지했으면 지우지 않고 경고(st.not_ours)를 결과에
붙입니다(progress의 정리 경고 대기열, CLI·GUI 작업 결과에 표시).
테스트: sectemp(destroy_leaves_a_file_that_took_the_name), engine_tests(part_guard_removes_only_its_own_file).

        "not a usable update file"로 거부해 root 헬퍼가 무엇이 있는지 알려 주지 않습니다.
        (2) 사본은 0600으로 만들고, 검증을 통과한 뒤 install_from_private에서 package.deb만 핸들로 0644로 바꿉니다
        (apt가 _apt 사용자로 읽음). (3) /var/lib/shield/update와 각 무작위 폴더는 0711(남은 목록을 못 봄).
        Windows는 사본 폴더가 SYSTEM·Administrators 전용이라 새로 읽히는 사람이 없고, 다른 관리자 계정으로 승격하는
        경우(over the shoulder) 다운로드한 계정과 승격 계정이 달라 소유자 규칙을 두지 않았습니다(update_input_owner_ok).
  파일: shield-core/src/update.rs, shield-platform/src/linux/install.rs, linux/mod.rs, windows/install.rs, windows/mod.rs
  테스트: linux::update_inputs_must_belong_to_the_pkexec_caller, update_folders_cannot_be_listed_by_others,

19-2. 업데이트 서명 정책 [낮음~중간]
  무엇: (a) 키 만료를 서명 시각 기준으로만 봤습니다. 서명 시각은 서명하는 쪽이 정하므로, 만료·교체된 배포 키가 새면
        과거 시각으로 서명한 가짜 설치 파일이 통과할 수 있었습니다. (b) 텍스트 서명(0x01)도 받았습니다.
        (c) 매니페스트에 발행 시각·만료가 없어 예전에 서명된 중간 버전을 다시 내밀 수 있습니다.
  수정: sigverify::Policy::Release를 더했습니다. 업데이트의 모든 서명 확인(대화 상자용 확인, 다운로드, 헬퍼의 사본
        확인; 매니페스트와 설치 파일 5곳)이 이 정책을 씁니다: 바이너리 서명(0x00)만, 주 키와 서명 부키가 오늘 기준으로도
        만료되지 않았을 것. shield verify와 자체 무결성 확인은 지금까지처럼 Policy::Any(서명 당시 유효하면 통과).
        현재 배포 키(8898 D3D9 ...)는 만료일이 없어 영향이 없습니다. 오류 문구 sig.key_expired_now(ko/en)를 더했습니다.
        (c)는 고치지 않았습니다: 줄을 더하면 3.0.0의 매니페스트 파서가 거부해 3.0.0 -> 3.1.0 업데이트가 끊깁니다(0-2).
        docs/01 7절에 한계로 적었습니다.
  파일: shield-core/src/sigverify.rs, update.rs, lang/ko_v3.rs, lang/en_v3.rs
  픽스처: tests/fixtures/pgp/k5_expired_later.asc(2020-01-01 생성, 2021-01-01 만료), data.k5.sig(2020-06-01).
        GnuPG 2.4 --faked-system-time과 버린 키링으로 만들고 공개키와 서명만 남겼습니다.
  테스트: sigverify::release_policy_refuses_keys_that_have_expired_since_signing, release_policy_takes_binary_signatures_only,
        key_expiry_now_rule_table, update::every_update_signature_uses_the_release_policy
        (기존 time_rules_table의 "key expired after signing is fine"은 일반 정책의 규칙이라 그대로 둡니다.)
  남은 한계: (c), 그리고 시스템 시계가 크게 틀리면 업데이트가 거부될 수 있음.

19-3. Windows 헬퍼의 secure_parent [낮음]
  무엇: 일반 사용자가 %ProgramData%\Shield를 미리 만들 수 있었고 MSI는 이 폴더를 만들지 않았습니다. 헬퍼는 이미 있는
        폴더를 symlink_metadata로 확인한 뒤 경로 문자열로 SetNamedSecurityInfoW를 불러 "인수"했으므로, 그 사이 정션으로
        바꾸면 관리자 권한으로 다른 폴더의 소유자와 DACL이 바뀔 수 있었습니다(접근 차단·ACL 변조).
  수정: (1) MSI가 %ProgramData%\Shield를 소유자 Administrators, SYSTEM·Administrators 전용, 상속 없음(헬퍼의
        ADMIN_DACL과 같은 SDDL)으로 만듭니다(구성 요소 UpdateDataFolder, 새 GUID 975C4053-...; 기존 GUID는 그대로).
        (2) 이미 있는 폴더는 정션·링크를 따라가지 않는 핸들(FILE_FLAG_OPEN_REPARSE_POINT | BACKUP_SEMANTICS)로 열고,
        그 핸들에서 실제 폴더인지와 소유자를 확인합니다. 소유자가 SYSTEM·Administrators·TrustedInstaller가 아니면
        넘겨받지 않고 중단합니다(그 계정이 미리 열어 둔 핸들로 계속 접근할 수 있으므로). 관리자 소유면 같은 핸들에
        SetSecurityInfo로 DACL만 다시 씌웁니다. 경로로 보안 정보를 바꾸는 코드는 없습니다.
  파일: shield-platform/src/windows/install.rs, installer/windows/installer.wxs
  테스트: windows::update_folder_owners_that_count, a_folder_made_by_a_normal_account_or_a_junction_is_refused_unchanged,
        release_tests::the_msi_creates_the_update_folder_with_the_helper_dacl, installer_components_are_stable_and_single
        (고정 GUID 목록에 UpdateDataFolder 추가)
  남은 한계: 설치 전에 일반 계정이 만든 폴더가 있으면 관리자가 지울 때까지 업데이트가 안 됩니다(docs/01). 승격된 경로
        (관리자 소유 폴더 다시 잠그기)와 MSI 권한 적용은 실기 확인 못 함(17절).

19-4. 새 기능: 폴더나 여러 항목은 아카이브 이름의 폴더 안에 복호화
  무엇: 전체 복호화(암호화 창, 우클릭 복호화, shield decrypt, 관리자 창 [전체 풀기])가 결과를 .shd 이름에 맞춰
        놓습니다. 사용자와 정한 규칙("자동"): 파일 하나 -> 그 파일 그대로. 폴더 하나 -> 이름이 .shd 이름과 같으면(대소문자
        무시) 그 폴더 그대로(photos/photos를 만들지 않음), 다르면 .shd 이름의 폴더 안에. 여러 항목·빈 아카이브 -> .shd
        이름의 폴더 안에. 3.0.0까지는 여러 항목일 때 컨테이너 안에 기록된 이름의 폴더를 썼고, 폴더 하나는 항상 그대로였습니다.
        이제 폴더 이름은 지금의 .shd 파일 이름에서 정합니다. [선택 항목 풀기]는 사용자가 고른 폴더에 그대로 풉니다.
        감싸는 폴더는 지금까지 여러 항목일 때처럼 사용자 전용 준비 폴더를 그대로 옮긴 것이라 본인만 접근할 수 있습니다.
        이름이 이미 있으면 "(decrypted)"를 붙이고 덮어쓰지 않습니다.
  파일: shield-core/src/engine.rs(out_folder, do_decrypt), docs/03 5절(+en)
  테스트: engine::several_items_or_a_renamed_folder_come_out_in_a_folder_named_after_the_archive, output_folder_rule_table,
        cross_os_tests 기대 위치 변경(16절)

19-5. 추가 점검
