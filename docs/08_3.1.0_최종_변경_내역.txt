0. 버전과 이 문서의 범위
------------------------
- 버전 번호는 3.1.0 그대로입니다(Cargo.toml, MSI, 설치 파일명, --version, 정보 탭, 문서 모두 3.1.0;
  release_tests::one_version_and_no_pre_release_labels가 확인).
- "이전 3.1.0 빌드" = docs\06_3.1.0_수정_기록.txt 1~19절(3.0.0 검토 1~15번, 2차 검토)까지 반영한 빌드
  (2026-11-09 빌드, 산출물 dist\의 이전 파일). 같은 3.1.0 번호로 이미 누군가에게 전달됐을 수 있습니다.
- "3.1.0 최종(수정 후)" = 그 위에 이 문서의 변경(완전삭제, 개발 중 점검 항목 A-J, 4장 분석, 문서)을 더한 빌드.
- 두 빌드는 --version이 같으므로 구분하려면 파일 해시(SHA256SUMS.txt)나 아래 동작 차이로 확인하십시오:
  완전삭제 탭·shield wipe가 있으면 최종입니다.
- 3차 검토(제한 없는 읽기, 코드 주석 "3.1.0 review 3")는 배포되지 않은 중간 단계라 아래 A에 합쳐 적습니다.

1. 기능
-------
1-1. 새 기능: 완전삭제 (docs/10)
  - GUI "완전삭제" 탭, 콘솔 shield wipe, 우클릭 "SHIELD로 완전삭제"(Windows 클래식 메뉴, Linux Nautilus·Nemo·
    Dolphin·Thunar). 일반 파일·폴더는 경고 -> 한계 고지(확인란) -> 6자 코드(3초 대기, 3회 오답 중단) 3단계,
    .shd만이면 2단계. 차단 목록(시스템 폴더, 드라이브 루트·마운트 지점, 홈 루트, Shield 자체 파일, 특수 파일).
  - 약화 옵션("다시 묻지 않기" 등)은 없습니다. --yes는 완전삭제 확인을 대신하지 않습니다.
  - 기존 "암호화 후 원본 파쇄"는 확인 절차를 그대로 두고, 덮어쓰기 루프를 완전삭제와 같은 것(wipe::overwrite_with)
    으로 바꿨습니다. 결과(패턴, 버퍼, 동기화)는 같습니다.
1-2. CLI --allow-weak (E)
  - 경고가 있는 새 비밀번호(짧음, 흔한 단어, 패턴, 기본보다 낮은 PIM ...)는 터미널에서 직접 "예"라고 답하거나
    --allow-weak가 있을 때만 씁니다. 이전 3.1.0까지는 --yes가 이 경고도 통과시켰습니다.
1-3. 우클릭 암호화·완전삭제에서 쓸 수 없었던 항목 수 표시 (F, S-03)
1-4. 산출물 이름: 소스 zip이 Shield_Project_v3_1_0.zip -> Shield_Project_v3.1.0.zip(다른 파일과 같은 _v3.1.0 형식).

2. 보안 수정 (개발 중 점검 항목 A-J)
----------------------------
 A 제한 없는 파일 읽기 [중간, CWE-789/400]
   이전: 서명 파일을 전부 읽은 뒤 64KiB 검사, 서명 대상은 크기 확인 후 전부 메모리로, --key 공개키·settings.key 무제한.
   최종: shield_platform::bounded(열고 -> 핸들로 종류·크기 -> take(최대+1)). 서명 64KiB, 공개키 1MiB,
         settings.key 4KiB, 설정 파일·spool·저널·update_seen 등 각자 상한, 서명 대상은 스트리밍(최대 2GiB).
         clippy.toml이 std::fs::read / read_to_string / Read::read_to_end / read_to_string 사용을 금지(테스트 코드 제외),
         CI clippy -D warnings가 Windows·Linux 모두에서 강제.
 B 업데이트 매니페스트 재생·롤백·폐기 [중간]
   최종: 매 릴리스가 v1(Shield_v<V>_release.txt, 3.0.0이 읽는 형식, 변경 없음)과 v2(Shield_v<V>_release_v2.txt
         + .sig)를 함께 게시합니다. v2: version, release_id, issued_at, expires_at(+365일, 최대 400일),
         min_allowed_version, revoked_key(keys/revoked_keys.txt), sha256 줄. 서명 대상은 파일 전체.
         3.1.0 최종 클라이언트: v2가 없거나 검증에 실패하면 자동 설치하지 않고 릴리스 페이지 링크만 보입니다.
         거부: 만료, 발행 시각이 24시간 넘게 미래, min_allowed_version > version, 현재 버전 이하(다운그레이드),
         서명 키가 폐기 목록에 있음, 지금까지 본 release_id보다 작음·본 적 있는 최소 버전보다 낮음(롤백).
         롤백 상태는 데이터 폴더의 update_seen.txt(사용자 전용 파일)에 둡니다. 없거나 손상되면 상태가 비며(지금 버전보다
         새것만 받는 규칙은 남음), 받지 말아야 할 것을 받게 되지는 않습니다. MAC 보호 설정에 두지 않은 이유: docs/09 B.
         안내 문구: upd.m_expired, upd.m_future(시계 확인), upd.m_rollback, upd.m_revoked (ko/en).
   호환성: 3.0.0과 이전 3.1.0 빌드는 v1만 읽고 v2 줄을 모릅니다(3.0.0 파서는 compat_tests로 고정). 그래서 v1을
         계속 같이 게시합니다. 이 클라이언트들은 재생·롤백 보호를 받지 못하고, 3.1.0 최종 이상으로 올라온 뒤부터
         보호됩니다. v1 중단 일정: 3.1.0 최종 게시 후 최소 12개월은 v1을 같이 게시하고, 중단은 릴리스 노트로 미리
         알립니다. 중단 뒤 3.0.0·이전 3.1.0 사용자는 자동 업데이트가 안 되므로 설치 파일을 직접 받아야 합니다.
 C 번들 릴리스 키와 운영 모델 불일치 [중간, 당시 기록]
   확인: keys/release_key.asc = 주 키 [SC] 만료 없음, [S] 부키 없음, [E] 부키, 개인 메일 사용자 ID.
   최종: (1) 테스트 픽스처를 테스트 전용 키로 분리(사용자 ID @invalid), 실제 키 사본이 픽스처에 없음을 테스트,
         고정 지문 테스트는 저장소의 keys/release_key.asc를 직접 읽음. (2) 백업 공개키 슬롯(keys/release_key_backup.asc,
         SHIELD_PUBKEY_BACKUP_PATH)과 "주 + 백업" 신뢰 목록(3.1.0 #3부터). (3) 새 릴리스 키 게이트: Cert::shape()가 키
         구조를 읽고 release_tests::release_key_gate가 서명 부키(만료 있음, 약 2년 이내), 인증 전용 주 키, 프로젝트
         사용자 ID(개인 메일 도메인 아님), 백업 키 파일을 검사. 태그 릴리스의 audit 잡에서 실행되어 통과하지 못하면
         빌드·서명·게시가 진행되지 않습니다. 로컬 build.ps1/build.sh는 같은 검사를 경고로 출력합니다.
         (4) docs/07 전면 개정(키 생성·운영·교체·폐기, 수동 GitHub 설정 체크리스트).
   당시 상태(후속 수정 전): 해당 키 구조를 요구하는 태그 게이트가 있었습니다. 2026-11-11 후속 수정에서 이
   키 모양 게이트를 제거했으므로, 아래 후속 수정 기록 이후에는 이 문장을 현재 상태로 적용하지 않습니다.
 D Linux 설정 폴더 /tmp/shield 폴백 [낮음]
   최종: XDG_CONFIG_HOME(절대 경로일 때만) 또는 $HOME/.config. 둘 다 없으면 오류(설정을 읽거나 저장하지 않음).
         설정 폴더는 실제 폴더(링크 아님)·현재 사용자 소유·0700(느슨하면 0700으로 조임). 설정 파일은 다른 사람이
         쓸 수 없어야 하고, settings.key는 본인 소유 0600이어야 씁니다(열린 핸들로 확인). 잠금 파일도 다른 곳에 만들지
         않습니다.
 E 약한 비밀번호와 CLI --yes [낮음]
   기준(한 곳: password::check_new, engine::check_new_password; GUI·설정 비밀번호·CLI 공통):
     거부(blocks): 빈 비밀번호(키 파일이 없을 때), 기본(12)보다 낮은 PIM + 키 파일 없음 + 20자 미만, 확인 불일치,
                   입력 버퍼 초과.
     경고(warnings): 13자 미만, 숫자만·한 종류 글자만, 흔한 비밀번호·포함, 반복·연속 패턴, 이름·사용자 이름 포함,
                   점수 낮음, 키 파일만 있고 비밀번호 없음.
   키 파일이 있으면 빈 비밀번호도 허용(경고)되고 PIM 최소 길이 규칙이 없어집니다(engine::min_password_len).
   GUI: 경고 후 "그래도 사용" 허용 정책 유지. CLI: --yes로 통과 불가, --allow-weak 또는 터미널 확인만.
 F Nautilus 상대 경로 [낮음, 기능 결함]
   최종: Nautilus 스크립트 3개(암호화·열기·완전삭제)가 같은 블록으로 경로를 절대화합니다.
         $NAUTILUS_SCRIPT_SELECTED_FILE_PATHS는 인자와 1:1로 맞을 때(각 줄이 절대 경로이고 "/<인자>"로 끝남)만 쓰고,
         이름에 줄바꿈이 있어 모호하면 각 인자를 $PWD 기준으로 절대화합니다. 이름은 평가·실행되지 않습니다.
         GUI는 인자를 다시 정규화합니다(file:// URI 해석, 상대 경로 -> 현재 폴더, . 제거, 링크 비추종).
         spool은 NUL 구분(S-01), 버린 항목 수를 암호화 창·완전삭제 탭에 표시.
   테스트: installer/linux/tests/nautilus_scripts_test.sh(공백·따옴표·$( )·백틱·줄바꿈·file://·검색 보기 등 47개,
         dash·bash, build.sh가 실행), release_tests::nautilus_scripts_share_the_absolute_path_block.
   실제 Nautilus에서는 실기 미검증.
 G CI 서명 구간 [낮음]
   최종: rust-toolchain.toml(1.99.1, clippy·rustfmt), 러너 windows-2022 / ubuntu-24.04 / ubuntu-24.04-arm,
         actions 커밋 SHA 고정, 빌드 산출물 provenance 증명(attest-build-provenance) + 서명 잡이 서명 전에
         gh attestation verify(이 저장소의 이 워크플로가 만든 같은 SHA-256인지), run: 안에는 ${{ }}를 넣지 않음(env:와
         GITHUB_* 변수만, 테스트로 강제), appimagetool은 URL + SHA-256 고정, audit 잡(cargo audit --deny warnings,
         cargo deny, 예외 재검토일 검사, 태그일 때 릴리스 키 게이트), 빌드 경로 재매핑(S-05).
         재현 가능 빌드: --remap-path-prefix는 적용, SOURCE_DATE_EPOCH는 Rust 바이너리에 시각이 들어가지 않아 해당 없음
         (MSI·zip의 시각은 남음). 같은 바이트를 다시 만드는지는 확인하지 않았습니다.
   수동 설정(파일로 강제 불가): docs/07 7절 체크리스트. 워크플로는 GitHub에서 실행된 적이 없습니다.
 H 파일명 위장·압축 속성 [정보]
   최종: Cf(제로폭, bidi, 태그 문자 등)·Co(사용자 정의 영역)·비문자 거부/표시 시 <U+XXXX>, 보이는 글자 없이 놓인

         전체 거부), Zstd 프레임 헤더를 디코더 전에 검사(윈도 최대 32MiB, 블록 수 상한). LZMA2 사전 상한은 기존.

   egui 0.27·rfd 0.14·pgp 0.21 업그레이드는 하지 않았습니다(9절).

4. 호환성 영향
--------------
 - 컨테이너 형식: 바뀌지 않았습니다(v2, 2.x 열림, 1.x 안 열림). 교차 OS 픽스처 테스트 통과.
 - 설정 파일: 형식 같음. Linux에서 다른 사람이 쓸 수 있는 설정 파일, 0600이 아닌 settings.key는 쓰지 않습니다
   (Shield가 만든 파일은 처음부터 0600이라 보통 영향 없음). 설정 폴더 권한은 자동으로 0700이 됩니다.
 - 업데이트: 릴리스마다 v1 + v2 매니페스트(2절 B). 3.0.0 -> 3.1.0 최종 업데이트는 v1으로 그대로 됩니다.
 - CLI 스크립트: 약한 비밀번호를 --yes로 넘기던 스크립트는 --allow-weak가 필요합니다(아니면 아무것도 만들지 않고 종료 코드 1, 터미널에서 "아니요"면 5).
   새 종료 코드 7(PARTIAL), 8(REFUSED)은 shield wipe만 씁니다.
 - spool 항목 형식이 줄바꿈 -> NUL로 바뀜: 업그레이드 도중 옛 프로세스와 새 프로세스가 동시에 spool을 쓰는 경우
   옛 항목은 버려지고 개수가 표시됩니다(다시 선택하면 됨).
 - Nautilus 스크립트는 integrate.sh가 사용자 폴더에 복사하므로 패키지를 올려도 저절로 바뀌지 않습니다(5절).
 - 빌드: build.ps1/build.sh가 target\remap-paths.toml을 만들어 cargo에 --config로 넘깁니다(경로 재매핑). 플래그
   환경 변수는 쓰지 않습니다(.cargo\config.toml의 crt-static을 대신하게 되므로). 사용자가 RUSTFLAGS를 설정하면
   이전과 같이 config의 플래그 전체가 무시되니 빌드 스크립트와 함께 쓰지 마십시오.

5. 사용자 조치가 필요한 것
--------------------------
 - Linux Nautilus 사용자: 업그레이드 후 /usr/share/shield/integrate.sh를 본인 계정으로 다시 실행(새 스크립트 복사).
 - CLI 스크립트 사용자: 약한 비밀번호를 의도적으로 쓰는 스크립트에 --allow-weak 추가.
 - Linux에서 HOME이 없는 환경(일부 서비스 계정): XDG_CONFIG_HOME 또는 HOME을 설정해야 설정이 저장됩니다.
 - 배포자(개발자): 당시에는 docs/07의 키 교체와 백업 키 추가, GitHub 설정 체크리스트가 후속 작업이었습니다.
   태그 릴리스의 키 모양 게이트는 2026-11-11 후속 수정에서 제거되었으며 현재는 유효한 공개키와, 서명 시 일치하는
   서명 가능한 비밀키만 필요합니다.

6. 삭제·변경된 옵션
-------------------
 - 삭제: Linux /tmp/shield 설정 폴더 폴백.
 - 변경: CLI --yes는 약한 비밀번호 경고와 완전삭제 확인에 응답하지 않습니다(무시하고 안내 출력).
 - 추가: --allow-weak, shield wipe(--passes, -r/--recursive, --dry-run, --confirm-token, --i-understand-irreversible),
         GUI --wipe 실행 인자.

7. 업그레이드 방법
------------------
 - Windows: 새 MSI를 실행하면 이전 3.x를 정리하고 설치합니다(UpgradeCode 같음, 2.1.0+3.0.0 동시 설치 재발 방지
   테스트). 우클릭 "SHIELD로 완전삭제"가 함께 등록됩니다. 포터블은 파일 교체 후 설정에서 우클릭 등록을 다시 하십시오.
 - Linux: deb 재설치(sudo apt install ./shield_v3.1.0_amd64.deb) 또는 AppImage 교체, 그 뒤 integrate.sh.
 - 앱 안 업데이트: 3.1.0 최종부터 v2 매니페스트가 필요합니다. 같은 3.1.0 번호의 이전 빌드에서 최종으로는 앱 안
   업데이트가 되지 않습니다(버전이 같아 "새 버전 없음"). 설치 파일로 직접 바꾸십시오.

8. 알려진 한계
--------------
 - 완전삭제는 SSD/NVMe·스냅숏·COW·클라우드·백업에서 물리적 소거를 보장하지 못합니다(docs/10 5절).
 - 같은 사용자 권한의 악성 프로그램은 확인 절차·설정 키·롤백 상태를 우회할 수 있습니다.
 - MSI·exe에 Authenticode 서명이 없습니다(SmartScreen 경고, docs/04).
 - 독립적인 제3자 보안 감사를 받지 않았습니다. 정적 분석·자동 테스트 중심이며 실기 미검증 항목이 있습니다(docs/09 7절).
 - cargo fmt --check는 통과하지 않습니다(코드 베이스 전체가 rustfmt로 정리된 적이 없음; docs/09 R-7).

10. 2026-11-11 후속 수정 및 정정
----------------------------------
- C항의 릴리스 키 게이트는 당시 추가되었던 정책의 기록이며, 현재 필수 조건이 아닙니다. 서명 부키·만료·프로젝트 사용자 ID·백업 공개키를 요구하던 태그 게이트와 고정 지문 테스트를 제거했습니다. 유효한 공개키는 필요하고, 서명 배포에는 이에 일치하는 서명 가능한 비밀키가 필요합니다.
- Shield 데이터 폴더 아래 파일·하위 폴더를 직접 선택하는 완전삭제 경로 검사 오류를 수정하고 회귀 테스트를 추가했습니다. 보호 경로와 선택 경로를 양방향으로 검사합니다.
- 권한 상승 업데이트 헬퍼에 보호된 시스템 공용 롤백 상태와 교차 프로세스 잠금을 추가해 동시 업데이트가 롤백 기준을 낮추지 못하게 했습니다.
