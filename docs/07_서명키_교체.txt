SHIELD 3.1.0 - 릴리스 서명 키 운영과 교체
===========================================
English: docs/en/07_key_rotation.txt

0. 현재 상태와 빌드 조건
------------------------
- keys\release_key.asc는 유효한 OpenPGP 공개키입니다. 현재 공개키는 주 키가 인증과 서명을 함께 허용하고
  만료일이 없으며, 암호화 부키만 있습니다. 사용자 ID는 개인 이메일입니다.
- keys\release_key_backup.asc는 선택 사항입니다. 파일이 있으면 보조 신뢰 키로 내장하고, 없어도 빌드와
  서명 검증은 정상적으로 동작합니다.
- **서명 부키, 만료일, 프로젝트 전용 사용자 ID, 백업 키는 빌드·테스트·태그 릴리스의 필수 조건이 아닙니다.**
  이러한 구성은 키 유출 피해를 줄이는 권장 운영 방식이지 프로그램의 암호 검증 규칙이 아닙니다.
- 빌드에 필요한 것은 파싱 가능한 공개키입니다. build.rs는 ASCII-armored 공개키만 내장하며 비밀키가
  들어 있으면 거부합니다. `--no-sign` 빌드에는 개인키가 필요하지 않습니다.
- 파일이나 릴리스를 GPG로 서명하려면 `keys\release_key.asc`와 일치하는 서명 가능한 비밀키가 필요합니다.
  이는 서명 자체를 만들기 위한 필수 조건입니다. 키 형태의 권장 조건과는 별개입니다.
- 현재 키는 서명 가능한 주 키를 사용하므로 별도 서명 부키가 없어도 동작합니다. 만료일이 없는 키는
  시간 경과만으로 만료되지 않으므로 유출 시 폐기·교체와 새 공개키 배포가 더 중요합니다.

1. 권장 운영 모델 (선택 사항)
-----------------------------
  주 키 [C]          인증 전용으로 두고 비밀키는 오프라인 보관. 긴 유효기간 또는 만료 없음.
  서명 부키 [S]      1~2년 만료. CI에는 전용 서명 부키의 비밀 부분만 저장하는 방식을 권장합니다.
  폐기 인증서        주 키를 만들 때 생성하고 서로 다른 오프라인 매체 두 곳에 보관.
  백업 키            별도의 공개키를 선택적으로 내장하고 비밀키는 오프라인 보관. 긴급 교체에 사용.
  사용자 ID          프로젝트 소유를 식별할 수 있는 주소 권장. 개인 이메일이어도 빌드 차단 사유는 아닙니다.
  폐기 목록          keys\revoked_keys.txt에 폐기된 주 키 지문을 기록합니다. v2 매니페스트가 이를 전달합니다.

  프로그램은 keys\release_key.asc를 기본 신뢰 키로 내장합니다. keys\release_key_backup.asc가 있으면
  보조 신뢰 키도 내장하며, 서명 검증은 둘 중 하나의 유효한 키로 생성된 서명을 받아들입니다.
  키 파일은 공개키여야 하며 최대 1 MiB입니다. 비밀키를 저장소나 공개키 파일에 넣지 마세요.

2. 새 키 생성 예시 (오프라인 컴퓨터에서 사람이 수행)
------------------------------------------------------
전용 서명 부키를 사용하는 권장 예시입니다. GnuPG 2.2 이상:
  gpg --quick-generate-key "Shield release signing <release@example.org>" ed25519 cert 5y
  gpg --list-keys --with-colons | grep ^fpr        (주 키 지문 FPR)
  gpg --quick-add-key FPR ed25519 sign 2y           (선택: 2년 만료 서명 부키)
  gpg --output revoke_FPR.asc --gen-revoke FPR      (폐기 인증서)
  gpg --armor --export FPR > release_key.asc        (공개키 -> keys\release_key.asc)
  gpg --armor --export-secret-subkeys SUBFPR! > ci_signing_subkey.asc  (선택: CI용 서명 부키 비밀만)
  gpg --armor --export-secret-keys FPR > main_secret.asc               (주 키 비밀, 오프라인 백업만)

전용 부키를 만들지 않는 경우에도 서명 권한이 있는 주 키의 비밀키로 서명할 수 있습니다. 단, 주 키가
온라인 CI 환경에 노출되면 주 키 전체의 폐기·교체가 필요할 수 있어 전용 부키 사용을 권장합니다.

- GitHub Actions에서 서명하려면 환경 `release-signing`에 `SHIELD_GPG_KEY`와
  `SHIELD_GPG_PASSPHRASE`를 설정합니다. 전용 부키를 쓸 경우 `--export-secret-subkeys`로 내보낸 부키를
  사용합니다. 주 키 비밀키 전체를 CI에 넣는 것은 기술적으로 가능하지만 권장하지 않습니다.
- 공개키와 서명키가 일치하는지 실제 서명 후 `gpg --verify`로 검증합니다. 일치하지 않으면 서명 단계가
  실패합니다. 빌드 테스트는 특정 지문을 소스에 고정하지 않으므로, 키 교체 때 테스트 파일을 수정할
  필요는 없습니다.
- 지문은 저장소 외부의 독립된 경로에도 게시하고 다운로드한 공개키와 비교하세요.

3. 선택적 백업 키
-----------------
  gpg --quick-generate-key "Shield release backup <release-backup@example.org>" ed25519 sign 0
  gpg --armor --export <backup fingerprint> > release_key_backup.asc
  gpg --armor --export-secret-keys <backup fingerprint> > backup_secret.asc
  공개키만 keys\release_key_backup.asc에 두고 비밀키는 오프라인 매체에만 보관합니다.
  백업 공개키를 만들지 않아도 빌드와 현재 키의 서명 검증은 동작합니다.

4. 기존 키에서 새 키로 전환
---------------------------
이전 버전이 기존 키만 신뢰한다면 새 키로 서명한 업데이트를 검증하지 못할 수 있습니다.
- 기존 키를 신뢰하는 설치가 없다면, 새 공개키를 포함한 새 설치 파일을 배포하고 외부 채널로 지문을 알립니다.
- 기존 키를 신뢰하는 설치가 있다면, 기존 키로 서명된 전환 릴리스에 새 공개키를 포함하는 단계가 필요할 수
  있습니다. 그 후 새 키로 서명하고 `keys\revoked_keys.txt` 및 v2 매니페스트로 기존 키를 폐기합니다.
- 백업 키를 사용한 긴급 전환 역시 프로그램에 그 백업 공개키가 포함된 버전에서만 자동 검증할 수 있습니다.

5. 정기 운영 체크리스트
----------------------
- 전용 서명 부키를 쓴다면 만료 3개월 전에 연장하거나 새 부키를 만들고 공개키를 다시 배포합니다.
- v2 매니페스트는 발행 후 365일 유효합니다. 자동 업데이트가 계속 필요하면 최신 패키지 해시로 매니페스트를
  다시 발행·서명합니다.
- 모든 릴리스에서 서명 검증, SHA-256, 공개 지문, CI 출처 증명을 확인합니다.
- `.cargo/audit.toml`의 의존성 권고 재검토 기한을 확인합니다.
- 폐기 인증서와 오프라인 백업 매체를 주기적으로 확인합니다.

6. 유출과 분실
--------------
- 서명 부키가 유출되면 해당 부키를 폐기하고 새 부키를 만듭니다. 새 공개키를 내장한 버전을 배포합니다.
- 주 키가 유출되면 기존 주 키를 폐기하고 새 주 키를 배포합니다. 기존 지문을 `keys\revoked_keys.txt`에
  추가하고 v2 매니페스트에 반영합니다.
- 백업 키가 유출되면 새 백업 공개키를 포함한 릴리스를 배포하고 기존 지문을 폐기 목록에 추가합니다.
- 주 키와 백업 키를 모두 잃거나 유출하면 기존 설치의 자동 복구가 불가능할 수 있습니다. 사용자는 새 설치
  파일을 내려받고 외부 채널에 게시된 지문을 확인해야 합니다.

7. GitHub 수동 설정 (서명 릴리스를 운영할 때)
---------------------------------------------
  [ ] Settings > Environments > release-signing: 승인자 및 태그 제한 설정.
  [ ] SHIELD_GPG_KEY / SHIELD_GPG_PASSPHRASE는 이 환경에만 저장하고 저장소 일반 시크릿으로 두지 않습니다.
  [ ] 태그 생성·삭제·변경 권한과 기본 브랜치를 보호합니다.
  [ ] Actions 권한은 필요한 최소 범위로 설정하고 외부 Actions는 고정된 커밋을 사용합니다.
  [ ] 공개 저장소 또는 지원되는 GitHub 환경에서 빌드 출처 증명을 사용합니다.

8. 보안 범위와 한계
-------------------
- 빌드에는 유효한 공개키가 필요하지만 특별한 키 구조나 백업 키는 요구하지 않습니다.
- 서명된 릴리스에는 공개키와 일치하는 비밀키가 필요합니다. 서명 비밀키가 없으면 `--no-sign`으로 빌드할
  수 있지만, 그 산출물은 서명된 정식 다운로드와 같지 않습니다.
- 업데이트는 서명·해시·버전·유효기간·폐기 목록을 검사합니다. 키에 만료일이 있으면 만료된 키의 업데이트
  서명은 거부됩니다. 만료일이 없는 키는 시간만으로 만료되지 않으므로 외부 지문 확인과 신속한 폐기가 중요합니다.
- 프로그램은 OpenPGP 폐기 정보를 인터넷에서 자동으로 가져오지 않습니다. 새 공개키를 포함한 프로그램과
  v2 매니페스트의 폐기 목록을 통해 전달됩니다.
- MSI와 프로그램 파일에는 Authenticode 서명이 없습니다. GPG 서명 확인 방법은 docs\04를 참고하세요.
