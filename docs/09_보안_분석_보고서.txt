SHIELD 3.1.0 최종 - 보안 분석 보고서
===================================
English: docs\en\09_security_report.txt
대상: 3.1.0 최종 및 2026-11-11 후속 수정 소스(4개 크레이트, 설치 파일 정의, 빌드 스크립트, CI 워크플로). 작성 2026-11-11.

0. 이 보고서의 성격 (먼저 읽으십시오)
------------------------------------
- 독립적인 제3자 보안 감사를 받지 않았습니다. 개발 과정에서 개발자와 AI 도구가 소스를 읽고 테스트를 만들어
  확인한 내부 점검입니다.
- 정적 분석(소스 읽기, grep, 타입 구조 확인)과 자동 테스트 중심입니다. 실제 장비·환경에서 확인하지 못한 항목이
  있으며 "실기 미검증"으로 표시했습니다(7절).
- "취약점이 없다"는 뜻이 아닙니다. 찾지 못한 것은 찾지 못했다고 적었습니다.
- 등급: 상(원격·무인증으로 기밀성·무결성 침해) / 중(조건이 있지만 실제 피해 가능) / 하(제한된 조건·영향) /
  정보(취약점은 아니지만 고쳐 둔 것, 또는 사실 고지).

1. 범위와 방법
--------------
- 입력 경계: 컨테이너 헤더·메타데이터·아카이브(7z/LZMA2/Zstd), 설정 파일·settings.key, spool, 업데이트
  매니페스트(v1/v2)와 서명, 명령줄·환경 변수, 드래그 앤 드롭·파일 관리자 인자.
- 권한 경계: Windows UAC 업데이트 헬퍼·TRIM 헬퍼, Linux pkexec 헬퍼, MSI 등록 항목, 우클릭 메뉴.
- 새 코드: 완전삭제(secure_delete, wipe_view, wipe_cmd, erase.rs) - 처음부터 4장 기준을 적용했습니다.
- 공급망: Cargo.lock(cargo audit 0.22.2, cargo deny 0.20.2), build.rs, build.ps1/build.sh, release.yml.
- 도구: cargo test(Windows 10, Docker Linux 컨테이너), cargo clippy -D warnings(양쪽 OS), clippy.toml
  disallowed-methods, 직접 작성한 회귀 테스트. 퍼징 도구(cargo-fuzz)는 쓰지 않았고 fuzz_tests.rs의 무작위 변형
  테스트만 있습니다.

4. 4장 점검 항목별 결과 (고칠 것을 찾지 못했거나 기존 대책을 다시 확인한 것)
---------------------------------------------------------------------------
4-1 입력 검증·자원
 - KDF 매개변수는 헤더에서 읽지 않습니다. Argon2id m=256MiB, p=4, t=3+PIM은 코드 상수이고(헤더에 마법 바이트·
   알고리즘 ID가 평문으로 없음), PIM은 사용자 입력이며 MAX_PIM=64로 제한됩니다. 헤더로 KDF 비용을 키우는 DoS 없음.
 - 아카이브: 항목 수 MAX_FILES, 깊이 64, 경로 1024자, 구성 요소 255바이트, 압축률 10,000배, LZMA2 사전·Zstd
   윈도 상한. fuzz_tests(무작위 변형 컨테이너, 깨진 7z)는 panic 없이 거부. 7z/Zstd 라이브러리 내부의 메모리·CPU
   사용은 검증한 것이 아니며, 위 상한으로 바깥에서 막을 뿐입니다.
 - 설정·spool·저널·매니페스트·서명·키 파일은 모두 크기 상한을 열린 핸들에 적용(A). spool 항목 10,000개, 완전삭제
   계획 200,000개.
 - 정수 변환: 청크 수·오프셋은 u64 + checked/saturating 연산(이전 점검 docs/05), 이번 새 코드(진행률·용량 합계)는
   saturating_add/mul.
4-2 암호 구현
 - 청크마다 nonce = 컨테이너별 무작위 접두 + 종류 표지 + 청크 번호(마지막 청크 표지 포함), AAD에 메타데이터 태그와
   형식 표지가 묶입니다. 재사용·순서 바꾸기·잘라내기는 기존 테스트(container_tests, fuzz_tests)로 확인.
 - 비교: 키 슬롯 DEK, 설정 MAC·검증자, 매니페스트 해시, 완전삭제 코드·토큰 모두 password::ct_eq(상수 시간).
 - 복호화 실패 메시지는 원인을 구분하지 않는 한 문장(err.bad / err.open_bad).
 - 난수: OS CSPRNG가 항상 기반이고 수집 엔트로피는 섞기만 합니다(entropy/). 실패 시 약해지지 않고 오류.
 - zeroize: 비밀번호 입력(SecretBuf), Cred, 키, 설정 키는 Zeroizing. 레지스터·스택·스왑·최대 절전 파일에 남는
   사본은 확인할 수 없습니다(docs/01 7절 고지).
 - 메모리 보호: VirtualLock/mlock, Windows 오류 대화 상자 끄기·DLL 검색 System32 한정·이미지 로드 정책,
   Linux RLIMIT_CORE=0·PR_SET_DUMPABLE=0. 실패하면 harden::degraded로 사용자에게 알리고 확인을 받습니다.
4-3 파일 시스템·경쟁
 - 완전삭제: 링크 비추종 열기, 핸들 기준 폴더 목록(fstatat/openat), 파일 ID 재대조, 이름 변경 후 핸들로 삭제(docs/10).
 - 임시 파일: sectemp(사용자 전용 폴더, O_EXCL/CREATE_NEW, 0600/소유자 ACL), 비정상 종료 뒤 저널 정리(기존).
 - spool: 사용자 전용 폴더가 아니면 쓰지 않음, 1분 넘은 항목·잘못된 항목 버림, 내용은 GUI가 다시 검사(신뢰 안 함).
 - 예약 장치 이름·8.3 이름·\\?\ 경로·ADS·대소문자: archive 이름 검사와 dup_key, 완전삭제의 경로 키(path_key).
4-4 설치·권한 경계
 - Windows: SetDefaultDllDirectories(System32), 레지스트리 명령은 실행 파일과 %1 모두 따옴표(테스트),
   MSI가 이전 버전 정리(UpgradeCode 고정, release_tests). %ProgramData%\Shield는 MSI가 관리자 전용 ACL로 생성.
 - Linux: pkexec는 절대 경로로만, 헬퍼 인자는 일반 파일·PKEXEC_UID 소유만, polkit auth_admin(기억 안 함).
 - 외부 프로세스: 절대 경로 후보만(xdg-open, pkexec, apt-get, dpkg, icacls, msiexec), 셸을 거치지 않음.
4-5 업데이트·네트워크
 - HTTPS 전용(리다이렉트 포함), rustls 인증서 검증, 리다이렉트 5회, 연결 10초·응답 20초 시간 제한, 설치 파일
   512MiB·작은 파일 상한, 허용 파일 이름 고정, 헬퍼가 사본을 다시 검증(2단계). 매니페스트 v2(B).
 - 서버가 거짓 응답을 주면: 서명 실패 -> 설치 안 함(링크만), 오래된 정상 서명본 -> 만료·롤백으로 거부(v2 클라이언트).
4-6 GUI·콘솔
 - 콘솔 비밀번호를 인자로 받는 기능은 기본 꺼짐(설정 allow_arg_secrets), 켜면 경고. 입력은 에코 없이.
 - 파일 이름의 제어 문자·위장 문자·긴 이름: S-09. GUI는 위장 문자를 <U+XXXX>로 표시(glyphs::code_only).
 - 클립보드 자동 삭제의 한계와 화면 캡처 방지의 환경 오류 표시는 3.0.0 방식 유지(docs/01).
4-7 공급망·빌드
 - build.rs: 네트워크 없음, 공개키 파일에 비밀키가 섞이면 빌드 중단, 저장소 URL 형식 검사.
 - 소스 zip: 비밀키 블록이 보이면 중단, keys/의 비밀키·.env 제외(release_tests). 경로 재매핑(S-05).
4-8 완전삭제 자체
 - 경로 해석 오류·상대 경로: 절대화 + 실제 경로 표시(relative_items_are_resolved_to_the_real_path).
 - 권한 우회: 같은 사용자 권한 이상은 쓰지 않음(UAC/pkexec 없음). 읽기 전용 해제는 확인 뒤, 핸들로.
 - 캡차 우회: ConfirmedWipePlan 봉인(compile_fail), 3초·3회·새 코드, 약화 설정 없음, --yes 무시.
 - 실패를 성공으로 보고: 패스 실패·0바이트 쓰기·삭제 실패·스트림 실패 모두 "일부/실패"(S-06, S-07).
 - 메모리: 버퍼 1MiB 하나, 계획 200,000개 상한.

5. 남은 위험과 수용 사유
------------------------
 R-1 같은 사용자 권한의 악성 프로그램: 설정 키(Linux는 0600 파일), 사용자 영역 update_seen.txt, 확인 절차를 우회할
     수 있습니다. 권한 상승 업데이트의 롤백 기준은 별도의 관리자/root 전용 파일과 잠금으로 보호되지만 관리자/root,
     커널 및 동일한 높은 권한의 공격자는 위협 모델 밖입니다(수용, docs/01 7절).
 R-2 SSD/NVMe·스냅숏·COW·클라우드: 덮어쓰기와 TRIM으로 물리적 소거를 보장할 수 없습니다(수용, UI 상시 고지).
     대책: 처음부터 암호화한 볼륨·컨테이너를 쓰는 것.
 R-3 번들 릴리스 키의 운영상 하드닝: 현재 키에는 별도 서명 부키·만료·프로젝트 사용자 ID·백업 키가 없습니다.
     이는 권고 사항이지 암호학적 유효성이나 빌드의 필수 조건은 아닙니다. 서명된 릴리스에는 내장 공개키와 일치하는
     서명 가능한 비밀키가 필요합니다. 전용 서명 부키와 오프라인 백업 키는 위험 감소를 위해 권장합니다(docs/07).
 R-4 MSI·실행 파일에 Authenticode 서명이 없습니다: SmartScreen 경고가 나오고, 사용자는 GPG .sig로 확인해야 합니다
     (docs/04). 인증서 비용·관리 문제로 이번에 하지 않음(수용).
 R-5 오래된 GUI 스택(egui 0.27, rfd 0.14)과 pgp 0.21에서 오는 권고 예외 8건: 영향 경로 분석상 Shield가 쓰지 않는
     기능(rsa 비밀키 연산, webbrowser - 링크 차단), Windows·Linux 빌드에 들어가지 않는 의존성(paste: macOS용 metal),
     또는 고칠 수 있는 버전이 GUI 스택 업그레이드를 요구하는 것(ttf-parser, zbus 계열)입니다. 각 항목의 이유는
     .cargo/audit.toml에 있습니다. 이 판단은 개발 중 분석이며 독립 검증을 받지 않았습니다. 2027-05-10까지 재검토.
 R-6 3.0.0·이전 3.1.0 클라이언트는 v1 매니페스트만 읽어 재생·롤백 보호를 받지 못합니다. 3.1.0 최종으로 올라온
     뒤부터 효력(docs/08 B).
 R-7 rustfmt: cargo fmt --check가 1,473곳 차이를 보고합니다(코드 베이스가 rustfmt로 정리된 적 없음). 동작과 무관하며
     일괄 정리는 리뷰가 어려워 이번에 하지 않았습니다.

8. 2026-11-11 후속 수정 기록
----------------------------
- 라이선스: 루트 LICENSE와 Cargo workspace 및 네 하위 크레이트의 license.workspace 메타데이터를 Apache-2.0으로 통일했습니다. deny.toml의 허용 목록도 Apache-2.0을 포함하며 GPL-3.0-or-later 선언은 제거했습니다.
- 완전삭제 보호: Guard::check가 선택 경로와 보호 경로를 양방향으로 비교하도록 수정했습니다. Shield 데이터 폴더 자체·조상뿐 아니라 settings, settings.key, 저널 등 내부 파일과 하위 폴더를 직접 선택하는 것도 거부하는 회귀 테스트를 추가했습니다.
- 업데이트 롤백: 권한 상승 설치 헬퍼가 ProgramData /var/lib의 보호된 시스템 공용 상태를 검사하고 저장합니다. 시스템 상태는 비정상 UTF-8·깨진 레코드·비정규 형식을 fail-closed로 거부합니다. 별도 잠금 파일로 롤백 상태 확인·저장·설치를 직렬화하여 동시 실행이 오래된 상태로 덮어쓰지 못하게 했습니다.
- 릴리스 키 정책: 특정 서명 부키, 만료일, 프로젝트 사용자 ID, 백업 공개키를 강제하는 태그 릴리스 게이트와 고정 지문 테스트를 제거했습니다. 유효한 공개키는 계속 필수이고, 서명된 배포에는 일치하는 서명 가능한 비밀키가 필요합니다.
- 문서: 기존 3.1.0 최종 변경 기록의 릴리스 키 게이트 설명은 당시 이력입니다. 이 후속 수정으로 현재 필수 게이트가 아님을 README, 빌드 안내, 키 운영 문서에 명시했습니다. 라이선스와 보안 보장 범위도 동기화했습니다.
- 검증 한계: 이번 작업 환경에는 cargo/rustc가 없어 새 Rust 코드와 테스트를 재빌드·재실행하지 못했습니다. 따라서 새 테스트가 통과했다고 주장하지 않습니다. 셸 문법·정적 문자열/문서 대조는 별도로 수행하고, 최종 Windows/Linux 전체 테스트와 clippy는 Rust 도구가 있는 CI에서 실행해야 합니다. GitHub Actions, UAC/pkexec, 실제 MSI/deb/AppImage 설치도 이 환경에서 실기 검증하지 않았습니다.
